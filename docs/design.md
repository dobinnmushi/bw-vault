# 設計の判断と教訓

README に書かないこと（なぜそうしたか、何を却下したか、何を直したか）の記録。2026-11-17 時点。

## 前提

- 目的：保管庫の秘密を、「Bitwarden のマスターパスワード」か「sudo と同等の認証」を通さないと取れない状態にする。
- 脅威：自分のユーザーで動く、認証を通していないプログラム（悪意あるツール、書き換えられたツール）。
- 調べたこと：rbw-agent は、解錠すると同じユーザーの全プロセスの `Decrypt` に応える。メモリは `PR_SET_DUMPABLE=0` と Yama で既に守られていて、
  **穴はメモリではなく、ソケット**。同じユーザーの中には、プログラムを区別する権限の境界がない → 鍵を別のユーザーへ。
- 先例：Goldwarden（別デーモン＋ polkit で秘密ごとに確認。開発停止中。資料に「10 分のキャッシュ」とあるが、何を保存するかは未確認）、rbw 自身の `master_password_reprompt`
  （agent が暗号文の集合を持ち、該当の復号だけ再確認する）。rbw を無改造のまま、前に別プロセスの門を置く形にした（本家の追従が要らない）。

## 却下した案

| 案 | 理由 |
|---|---|
| TPM だけで鍵を封印する | TPM は同じユーザーの呼び出しを区別しない。区別させる条件（パスワード）は、結局マスターパスワードに戻る |
| 指紋を暗号鍵に使う | このセンサー（Goodix MOC）はチップ内で照合して「一致」と返すだけで、鍵を取り出せない。指紋は許可の判定にしか使えない |
| ユーザーの権限のまま、プログラム内で確認する／ソケットの権限で絞る | 同じユーザーは、ファイル・ソケット・設定・`~/.local/bin` の実行ファイルを、すべて迂回・書き換えできる |
| 一覧の認証に Howdy（顔認証）を使う | polkit は、アクションごとに PAM を選べない（常に `polkit-1`）。顔認証は操作を要さず、座っていれば、どのプログラムの要求も黙って通る。守りにならない |
| 「最初の認証だけ」で、一覧と項目を1回で済ませる | 確認画面に項目名を出せなくなり、別の項目を狙う要求を見破れない。承認の結び付け先が、ユーザー全体か、起動元の子孫になり、後者は書き換えられるツールが連鎖に並ぶ |
| 解錠のたびにマスターパスワードを、ユーザー側で入力する | 別ユーザーの agent は画面に出せない。ユーザー側の入力欄は、偽物に打たされる危険が残る。封印（TPM2）で入力の場面自体をなくした |

## 途中で見つかって、直した問題

1. **承認が、表示した項目に結び付いていなかった**（最初の実装）。「同じプロセスは 10 秒まとめる」が、プロセス全体に効いていて、
   1つの承認で、10 秒間はどの項目の秘密も取れた。確認画面の項目名が違うのに、本物の中身が返ってきたことで発覚。
   標準の `rbw get` が、探す段階で**全項目のノート**を復号するため、先頭の項目のノートで確認が出ていた。
   → 承認を「プロセス＋項目」に結び付け、秘密は項目単位の `GetEntry` だけにした。標準の `Decrypt` は、秘密の欄を断る。
2. **一覧（項目名・ユーザー名）が認証なし**だった（最初の設計判断）。「機密情報は認証なしに取れない」の目的に照らして、穴だった。→ `list` の確認を足した。
   承認は、1回の操作で別々のプロセスが一覧を取るので、ユーザー全体の 20 秒の窓にした（窓の間に見えるのは名前だけ）。
3. **記録（journal）に項目名を書いていた。** `adm` グループのユーザーは、システムの journal を読める。→ 短い識別子（ハッシュの先頭 8 文字）だけにした。
   すでに書かれた過去の記録は、journald が行単位では消せない（消すなら `journalctl --vacuum-…` で、システム全体の過去の記録に及ぶ）。実施したかは未確認。
4. **SSH 署名の承認が、全プロセスに効いていた**（旧 bw-ssh-agent の「30 秒、全プロセス」を引き継いだ）。→ 親プロセス＋鍵に結び付けた。
5. **セットアップスクリプトが、本物の rbw をラッパーで上書きした。** `~/.local/bin/rbw` をラッパーに差し替えたあとで再実行し、
   スクリプトがそのリンク先（ラッパー）を root 所有の置き場にコピーした。→ ELF の実行ファイルだけを置き、置き済みの本物は上書きしない。
6. **再起動で初めて出る不具合：** `bwvault-ssh.service` に `WantedBy=sockets.target` を付けたサービスは、既定の依存（`basic.target` のあと）と
   起動順の循環になり、起動時に取り消される。手で `enable --now` したときは動いていた。→ `DefaultDependencies=no`。`systemd-analyze --user verify` で再現できる。
7. **rofi-rbw の TOTP は `rbw code` を呼ぶ。** 「code は使われていない」と思い込んで断る仕様にしていた。→ `bwv code`（RFC 6238 の試験値で確認）。
8. **導入スクリプトが、書き換えられるフォルダのファイルを、root で、システムの大事な場所へコピーしていた**（`/etc/pam.d/polkit-1`、gate、pinentry、
   unit、rbw の実行ファイル）。同じユーザーの悪意のあるプログラムが先に書き換えていれば、次の更新で、そのまま root・`bwvault` の権限で動く（セキュリティの査読で発見）。
   → 入れる前に、root 所有の一時置き場へ写して、差分を表示し、`yes` を求める。PAM は別の確認を省けない。rbw はハッシュ照合。改ざんを入れた複製と、
   確認の部分を壊した版（変異）で、試験が失敗することを確認した。残る限界：差分を読んで気づくのは人。写しの表示と入れる内容の一致は、読んで確かめた（root での実行は試験できていない）。
9. **TOTP つき項目で、確認が重なりうる**（rofi-rbw のコードを読んで発見。実機での再現は未確認）。rofi-rbw は、パスワードを入力するとき、TOTP のある項目では
   `.totp` を2回呼び、そのたびに `rbw code` を実行する。私のラッパーでは、`rbw get` と `rbw code` は別のプロセスで、承認が「プロセス＋項目」だったため、
   同じ項目の確認が最大3回。→ 項目の承認を「親プロセス＋項目」に結び付けた（SSH と同じ。別の項目は必ず聞き直す）。**直す前に、同じ親の子プロセスで再現する試験を書き、
   失敗することを確かめてから直した。** 親が短命で、1回の操作ごとに別になる（rofi-rbw の子）ので、別のプログラムが引き継ぐ余地は小さい。
   親が長命の共通の祖先（シェルなど）のときは、同じ項目だけ10 秒共有される（別の項目は聞き直す）。
10. **試験の元ファイルを `/tmp` に置いていて、再起動で消えた。** 最初からリポジトリの `tests/` に置く（`/tmp` は tmpfs）。

## 速さ（2026-11-17 の計測）

「認証や画面の立ち上げがもっさりする」との指摘を受けて、測った。
- gate への1要求：約 1.2 ms（復号1件。gate が agent を呼ぶ分を含む）。**gate 自体は速い。**
- 遅さの正体は、**一覧の取得を何度もすること**：`rbw list --raw` は約 0.87 秒（483 件の復号を、1件ずつ別の接続で頼む）。ホットキー1回で、
  bw-autotype・rofi-rbw・`bwv get` の探索で、2〜3回走る（一覧だけで 2〜2.6 秒）。`rbw` を呼ぶごとに、ラッパーの固定費が約 60〜70 ms（Python を2回起動）。
- 対策：gate に `List`（1回の要求で一覧を返し、保管庫が変わるまで門の中で覚える）。ラッパーは `rbw list --raw` だけを `List` に差し替える。
  ラッパーの設定確認は、すでに整っていれば、Python を起動し直さない。
- 計測に含めていないもの：確認の画面が出るまで（polkit の補助プログラムの起動、fprintd の起動と、指紋リーダーの USB の再初期化。2026-11-17 の記録では、
  補助プログラムの起動から、指を置ける状態まで約 0.8 秒）。これは gate の外の部分で、gate からは縮められない。

この対策の途中で見つかった不具合（どれも試験で見つけた）:
- **無限ループ：** 古い gate（`List` を知らない）に戻る処理が、PATH 上の `rbw`（＝ラッパー自身）を呼び、ラッパーが `bwv` を呼ぶ、呼び合いになった
  （ユーザー側のリンクはすぐ有効になるので、gate を配備する前に、実機で起こりえた）。→ 従来の経路は、実体の rbw の絶対パスを呼ぶ。既定値そのものを試験で確かめる。
- ラッパーが `bwv` を読み込むとき、`__file__` が未定義で落ちた。
- `test_setup.py` が、実機の配備状態（配備済みかどうか）で結果が変わっていた。→ 偽の「システムの置き場」と比べる形にした。

## 試験の方針

- 偽の agent・偽の API・偽の polkit で、gate の約束を確かめる。**実際の polkit のダイアログと、実際の保管庫は、手で確かめた**（その結果はリポジトリには残っていない）。
- 変異試験：不具合（記録に名前を書く／一覧の確認を外す／承認を項目に結び付けない）をわざと入れた gate で、試験が失敗することを確かめた。通るだけの試験にしない。
- 実機でしか確かめられないこと：ダイアログの見た目と本文、指紋の再試行（`pam_fprintd` は 1 回の失敗ごとに待たず、指が乗ったまま次の照合が走る → 5 回にした）、
  再起動後の自動解錠（TPM2）、ログインし直したあとの `SSH_AUTH_SOCK`。

## ユーザー名だけを出すときは、2 回目の確認を出さない（実施済み。2026-11-17、利用者からの提案）

安全性は問題ない：ユーザー名は、一覧の確認（1 回目）で、すでに全項目分が見える。SSH の公開鍵は、`ssh-add -L` で、確認なしに取れる。新しい露出は生まれない。

- gate: `GetEntry` に `"public": true` を付けると、**一覧の確認だけで**、秘密を除いた欄（名前・フォルダ・Login のユーザー名と URI・SSH の公開鍵と指紋）だけを、
  同じ形で返す。ほかは null か空。`public` は真偽値の `true` のときだけ有効（文字列などは、通常の `GetEntry`）。
  **public で得た承認は、秘密に使えない**（通常の `GetEntry` は、そのあとでも項目の確認が出る。試験で確認）。
- `bwv get --public`。ラッパーは、そのまま通す。
- rofi-rbw のフォーク（`dobinnmushi/rofi-rbw`、ブランチ `fetch-public`）: キーの割り当てで対象が決まり、対象に秘密がない（ユーザー名・URI・Tab・Enter・待ちだけ）ときに、
  `rbw get --raw … --public` で取る。**環境変数 `ROFI_RBW_FETCH_PUBLIC=1` のときだけ**有効（引数ではなく環境変数にしたのは、古い rofi-rbw が「知らない引数」で落ちないように、
  bw-autotype が、gate があるときだけ設定できるため。普通の rbw は `--public` を知らないので、渡してはいけない）。
- 効くのは Alt+2（ユーザー名だけを入力）・Alt+u（ユーザー名をコピー）のような、対象がキーで決まる操作だけ。Enter（ユーザー名＋Tab＋パスワード）とメニュー（Alt+m）には効かない。
- 副産物：TOTP の有無（`totp is not None`）が false になるので、ユーザー名だけの操作で `rbw code` が呼ばれることも、なくなる。
